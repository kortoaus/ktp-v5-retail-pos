# POS 바코드 스캔 큐 설계 (미착수 — 오너 결정 2026-09-05)

상태: **설계 확정, 구현 대기.** 오너가 나중에 처리할 용도로 박제 (api-docs `/barcode-queue`).

## 배경 (2026-09-05 매장 실사에서 드러난 것)

- 멤버 QR 스캔이 간헐 실패("5번 중 1번 성공") 신고 → 추적 결과 근본 원인은
  `CRM_URL` 이 Cloudflare 왕복(`crm.ktpv5.com`)이라 매장 인터넷 순단마다
  pos_server→crm 연결이 ETIMEDOUT. **루프백 전환(`http://127.0.0.1:3013`)으로
  해소 확인.** 단, 서버를 심지 않은 원격 매장(템플릿 확장)은 루프백이 불가 —
  이 큐 설계가 그 대비책의 클라이언트 축이다.
- 그 과정에서 드러난 구조 결함: `SaleScreen/index.tsx` 스캔 콜백의
  `if (loading) return` 가드가 멤버/주문 조회가 도는 동안 **모든 스캔(아이템
  포함)을 조용히 드랍**한다. 느린 조회 중 찍은 상품이 소리 없이 증발.
- UX 결함: 스캔 조회 중 화면 피드백이 전무 — 캐셔는 스캐너 beep(바코드 읽음)과
  조회 완료를 구분할 수 없다. 검색 모달은 로딩 스크린이 있어 기다려주는데
  스캔은 없어서, 느린 응답이 전부 "고장"으로 인지된다.

## 확정 설계: 순차 처리 스캔 큐 (오너 제안)

fire-and-trigger 를 버리고, 스캔 입력을 전부 큐에 담아 워커가 하나씩 순차 처리한다.

**핵심 구분 (오너·세션 상호 확인 2026-09-05)**: 스캔 콜백은 **순수 생산자**다 —
바코드 문자열을 큐에 push 하고 즉시 반환하며, 콜백 안에서 await·조회·드랍용
early return 을 하지 않는다 (현행 `if (loading) return` 의 "버리기"가 사라지는
지점). 실제 핸들링(멤버 조회/주문 로드/아이템 추가)은 **분리된 소비자**(워커
루프든 함수든)가 전담하고, 하나가 끝나야 다음을 꺼낸다. 생산과 소비가 완전히
디커플이라 스캐너가 아무리 빨라도 유실이 불가능하다.

```
스캔 → 큐 append
  ├─ member%%% / order%%% : 동일 페이로드가 in-flight/대기 중이면 드랍(접기)
  └─ 상품 바코드 / PP      : 무조건 append — 찍는 횟수가 곧 수량 (접기 금지)
워커: 순차 처리 (단일 루프)
  - 네트워크 조회(멤버/주문)는 타임아웃 5초
  - 실패 시 토스트("멤버 조회 실패 — 재스캔 또는 전화번호 검색")만 내고
    큐는 계속 진행 — 실패가 큐를 죽이면 안 됨
UI: "처리 중: ○○ · 대기 N건" 비차단 칩 — 모달/블로커 금지
```

### 결정 근거 (오너 룰링, 재론 불요)

- **큐 순차 > 병렬 분기**: 스캔 유실 제로 + 찍은 순서 보존 + 단일 워커의 단순함.
- **블로킹 오버레이 금지**: 멤버 조회 중에도 캐셔는 아이템 스캔을 계속해야 한다.
- **중복 접기는 타입별**: 멤버/주문 QR 은 "조회"라 연타=한 번 의도 → 접기.
  상품/PP 는 **횟수=수량** (콜라 3병 = 3 beep = qty 3) → 절대 접지 않는다.
- **헤드 블로킹 트레이드오프 수용**: 네트워크 스캔이 큐 앞에서 느리면 뒤가
  기다리지만, 5초 타임아웃 + 처리중 칩으로 캡·가시화된다 (현행은 30초 침묵).

## 구현 범위 (착수 시)

1. **retail_pos_app** `SaleScreen` 스캔 파이프라인: 콜백 → 큐+워커로 재배선,
   `if (loading) return` 글로벌 가드 제거, 타입별 접기, 처리중/대기 칩(1366×768).
2. **retail_pos_server**: crm/api 호출 타임아웃 30s → 5s
   (`src/libs/cloud.api.ts` axios timeout).
3. 주문 QR 로드(카트 세팅)는 처리 중 해당 카트 조작만 잠그는 기존 의미 유지.
